## この文書のスコープ（重要）

このリポジトリには並行する2つのワークストリームがある。

1. **インフラ移行（Manus → 自社VPS自己ホスト）**: 本ドキュメントの主対象。このセッション（および直前の一連のクラウドセッション）が直接手を動かして経緯を把握している。
2. **アプリ機能開発（請求書・月締め・現場ビジョン/genba 等）**: 別セッション群が並行して進めている開発。意思決定の経緯はこのセッションの記憶にない。genba については `docs/genba/`（`migration_design_v1.1.md` / `ROADMAP.md` / `prototype/GenbaAppV18.jsx`）が正本ドキュメントなので、機能開発を引き継ぐ場合はそちらと `git log --grep genba` 相当の履歴を参照すること。本ドキュメントでは意思決定の理由を推測で書かない。

## プロジェクトが何か・完成の定義

充寵グループ（電気設備工事業）の業務管理システム。コーポレートサイト（日/pt/en）と、従業員・現場・出面・請求書・月締めを扱う管理アプリ（`/app`）。

- サーバー: Express + tRPC v11（`server/routers.ts` 単一 appRouter）
- DB: MariaDB 11 + drizzle-orm
- フロント: React + Vite + wouter
- テスト: vitest

**インフラ移行の完成の定義**（達成済み — 詳細は後述の検証レベル参照）:
Manus プラットフォームへの依存ゼロで、自社VPS上のみで本番稼働し続けられること。具体的には「コード push → イメージビルド → 自動デプロイ → DBマイグレーション自動適用 → ファイルストレージ自己ホスト → バックアップ自動化 → HTTPS → 基本的なセキュリティ強化」が全部自動化され、オーナー（iPhone + Termius のみ、PC非所持）が手動でVPS操作をほぼしなくて済む状態。

**アプリ機能開発の完成の定義**: 未定義（別ワークストリームの管轄。`docs/genba/ROADMAP.md` に M2〜M5 の DoD が定義されている）。

## 決定事項とその理由（「一度こうしてやめた」ものを含む）

- **オブジェクトストレージは MinIO 自己ホスト（Cloudflare R2 等は不採用）**: オーナーが外部クラウドストレージへの依存を明示的に拒否し、「俺のNASとか」「NASビシバシ使って」と指示。VPS内 docker で MinIO を稼働させ、presigned URL 方式（`server/storage.ts`）でブラウザが直接 `S3_ENDPOINT` から取得する構成にした。そのため `S3_ENDPOINT` は公開到達可能なドメイン（`storage.juchou-group.com`）である必要がある。
- **バックアップ先はオーナー自身のNAS（Synology）+ Google Drive**: サードパーティのバックアップサービスは使わない方針。VPS→NAS は NAS側からの pull（rsync、鍵認証、読み取り専用ユーザー `nasbackup`）。VPSを外部公開しない設計。NAS→Google Drive は Synology の Cloud Sync（NAS標準機能）。
- **完全自動デプロイ（VPS操作ゼロ）を選択**: オーナーに手動デプロイ方式との選択肢を提示し、「B」（Watchtowerによる全自動）を選択。main マージ後、オーナーが何もしなくても5〜10分で本番反映される。
- **Cookie は `sameSite: "lax"`**（`"none"` から変更）: `SameSite=None` は `Secure` 属性必須で、HTTPS導入前の暫定HTTP運用時にブラウザがCookieを破棄していた。HTTPS化した現在も `lax` のまま運用（`none`に戻す積極的理由がないため）。
- **`verifySession` は `openId` のみ必須に変更**（旧: openId+appId+name必須）: 自己ホストでは Manus OAuth の `appId`(=`VITE_APP_ID`) が空になるため、必須のままだと全ログインが「ログインが必要です」で弾かれた。
- **`server/_core/vite.ts` は vite を動的 import に変更**: 本番イメージに `vite`（devDependency）が存在せず、静的importだと起動時クラッシュ（`ERR_MODULE_NOT_FOUND`）していたため。esbuildにインライン化されないよう、import指定子を配列join経由で間接化している。
- **重複マイグレーション（0018/0021/0025など）は削除せず `SELECT 1;` へ no-op化**: drizzle-kit生成版と内容が重複しMariaDB 11で構文エラーになっていたが、journalエントリ自体を消すとmigratorの整合性が崩れるため、ファイルは残しno-op化する方式を選んだ。
- **マルチアーキ(amd64+arm64)イメージ**: 元々の依頼事項。現行VPSはx86_64のみでarm64は実運用では使っていない（将来のARM環境やローカルのApple Silicon開発機を見据えたビルドのみ）。
- **ufw は 22 のみ許可、80/443はDockerが直接公開**: Docker はufwのルールをバイパスして直接iptablesを操作するため、ufwの許可リストに80/443が無くても実際には開いている。これを知らずに「ufwで80/443を開けなきゃ」と再作業しないこと。

## 試したがダメだったこと（次回同じ失敗をしないために）

- **モバイル(Termius)からのヒアドキュメント貼り付けで複数行ファイルを作成 → 不可能と確認済み**: 改行がスペースに化けてファイルが壊れる。回避策: 1行のprintf/curlでファイルを生成するか、SFTPで転送する。
- **SSH秘密鍵をテキストとしてチャット経由でTermiusに貼り付け → 不可能と確認済み**: base64に余分なスペースが混入し鍵が壊れる。回避策: サーバー側で `ssh-keygen` して鍵ペアを生成し、秘密鍵ファイルをSFTPでTermiusへ転送する（テキストのコピペをしない）。
- **アプリコンテナ(port 3000)を直接ホストに公開 → 運用上不可**: ファイアウォール/ISP事情でポート3000の直接アクセスが安定しなかったため、80番に変更 →最終的にCaddyが80/443を占有しリバースプロキシでapp:3000へ転送する構成に落ち着いた。以後アプリを直接ポート公開する方式には戻さないこと。
- **Watchtowerのデフォルト設定 → 動かない**: `client version 1.25 too old` エラーが出た。`DOCKER_API_VERSION: "1.44"` を明示しないと新しめのDocker daemonと通信できない。

## 環境の落とし穴

- **MariaDB 11 前提**（MySQL 8ではない）。CI移行元(旧Manus)はTiDB(MySQL8互換)だったため、MariaDB固有の構文非互換が本番投入時に初めて顕在化した実績がある。`.github/workflows/build.yml` の `migration-test` ジョブがMariaDB 11実機でマイグレーションを流して検証するので、SQL非互換はpush時点で検出される。
- **本番バンドルは `esbuild --packages=external`**: devDependency（vite等）は本番イメージに存在しない前提。動的importにしないと本番でクラッシュする。
- **CI の Node バージョンが2箇所で不一致**: `ci.yml`(build-and-test) は Node 22、`build.yml` の `migration-test` ジョブは Node 20。ローカル/本番実行環境は Node 22。意図的な差分か単なる見落としかは未確認。動作に支障は出ていないが、触るときは注意。
- **`.env.example` はテンプレートであり実際の本番値ではない**: 例えば `S3_ENDPOINT`/`S3_FORCE_PATH_STYLE`はCloudflare R2を想定したサンプル値（`force_path_style=false`）になっているが、実際の本番 `.env` は MinIO 用の値（`S3_ENDPOINT=https://storage.juchou-group.com`、`S3_FORCE_PATH_STYLE=true`）で運用している。`.env.example` を鵜呑みにしてR2前提で作業しないこと。
- **Docker は ufw をバイパスする**（前述）。
- **`Caddyfile` はファイルであることが必須**: 存在しない状態で `docker compose up` すると Docker が同名ディレクトリを誤作成し `not a directory` エラーになる。
- **storageサブドメイン追加/変更時はcaddyを明示的に `--force-recreate` する必要がある**: compose差分の反映だけではcaddyが再作成されず、新ドメインの証明書取得が走らない。
- **秘密情報のセキュリティ制約（厳守）**: オーナーはパスワード・秘密鍵などの値を一切Claudeに渡さない方針（オーナー本人がVPS上で直接入力・`.env`に設定）。Claude側もリポジトリやチャットに秘密の値を書き出さないこと。

## 検証レベル（3段階）

### (a) 実データ・実環境で動作確認済み
- 本番VPSでのアプリ稼働、ログイン（Cookie/`verifySession`修正後、HTTPS経由）
- 旧Manus(TiDB)データの全27テーブル移行（オーナー確認: 移行後に新規データ入力なし → 再移行不要）
- ドメイン+HTTPS（Caddy／Let's Encrypt自動取得、`https://www.juchou-group.com/app`到達確認）
- MinIOストレージ: アプリからのPUTと、ブラウザからのpresigned URL GETの往復を実際に確認済み
- VPS側の日次バックアップ(`backup.sh`): DBダンプ(`juchou_*.sql.gz`)とMinIOファイル(`minio_*.tar.gz`)の両方が正しく生成されることを実行確認済み（MinIO側は一度不具合(バックアップが空/未対応)があり、修正後に22MBのtar.gzが生成されることを確認）
- Watchtowerによる自動デプロイ: `DOCKER_API_VERSION`修正後、実際のマージ→自動反映を確認済み
- fail2ban稼働、SSHパスワード認証の完全無効化（`sshd -T`で確認済み）、鍵認証でのログイン成功

### (b) 実装したが未検証（何が未確認か明記）
- **NASへのrsync自動取得 → Google Drive同期の完全なエンドツーエンド**: Synology側のタスクスケジューラ設定・鍵配置までは完了しているが、「VPSでbackup.shが生成した最新ファイルが、翌日のタスク実行で実際にNASへ届き、かつCloud SyncでGoogle Driveまで反映される」ところまでを一連で確認した記録がない。次回、VPSで手動 `backup.sh` 実行 → 数分〜翌日にNAS側で新規ファイルの有無とGoogle Drive側の反映を確認するとよい。
- **arm64イメージの実機起動**: CIのマルチアーキビルド・manifest検証(`linux/amd64`と`linux/arm64`両方の存在)はCI上で確認済みだが、実際にARM環境（例: Apple Silicon上のDocker）でコンテナを起動して動作させたことはない。現行VPSはx86_64のみでarm64は使っていない。

### (c) 未実装
- **旧Manusファイルの MinIO 移行**: 請求書PDF・ロゴ・資格証などの旧ファイルは今も AWS(Manus Forge, `d2xsxph8kpxj0f.cloudfront.net`)上にあり、DBにはそのURLが入ったまま。MinIOへのダウンロード→再アップロード→DBの `fileUrl`/`fileKey` 参照更新は未着手。Manus停止前に必須。
- **秘密情報のローテーション**: 移行作業中の画面共有でスクリーンショットに写った `JWT_SECRET` / DBパスワード / オーナーパスワードは未ローテーション。

## ユーザーの承認待ちで止めていること（勝手に進めない）

- **旧Manusファイルの移行**: オーナーは「後日でよい」と明言（緊急ではないが、Manus停止のタイミング次第では実質的な期限があるので、着手前に一声かけて実行タイミングを確認すること）。
- **秘密情報のローテーション**: 依頼されていない任意タスク。特に `JWT_SECRET` の変更は全セッションを無効化する（再ログインが必要）ため、実施前に必ずオーナーへ確認する。
- **genbaブランチのマージ**: `CLAUDE.md` の genba ルールにより、genba関連の変更は「ユーザー承認後」にマージする（＝インフラ系PRの自動マージポリシーとは別扱い。genbaは自動マージしない）。

## ユーザーの好み・却下されたもの（やり直し防止）

- 外部クラウドストレージ（Cloudflare R2など）は却下。ストレージは自己ホストMinIO、バックアップは自分のNAS+Google Drive。
- オーナーへの返信は日本語。
- 「CI待ち」等の途中経過メッセージは書かない（完了・要判断・失敗時のみ報告）。
- インフラ系PR: CI green（`ci.yml`のbuild-and-test と `build.yml`のmigration-test/build両方）になったら、都度確認せずdraft→ready→即マージ（merge method: `merge`）。マージ後の手動デプロイ/Publish依頼はしない（全自動で反映されるため）。
- genba関連の変更は上記と異なり、マージはユーザー承認後（自動マージしない）。
- **秘密情報（パスワード・秘密鍵・JWT_SECRET等の値）は絶対にオーナーからClaudeへ渡さない/Claudeも書き出さない**という運用が合意済み。値はオーナーがVPS上で直接入力するか`.env`に設定する。
